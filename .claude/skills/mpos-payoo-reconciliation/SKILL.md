## Overview

Accounting staff need to match card-terminal (mPOS) and online-payment (Payoo) transactions against existing `payment_line` rows inside PRs (payment requests). Neither mPOS nor Payoo exposes a public API. The solution is a Manifest V3 Chrome extension that runs in the accountant's browser, crawls both portals using the user's existing login session, and POSTs data to the FastAPI backend. Accounting staff then manually link each gateway transaction to a payment line inside **CardReconciliationTab**.

**Scope: read-and-reconcile only.** The extension never writes to mPOS/Payoo portals. The backend never touches the `payment_request` or `payment_line` create/status flows.

## Why a Chrome extension is required

Both portals use **session-based authentication** (HTTP-only cookies set after browser login). There is no OAuth or API key mechanism available. A server-side crawler cannot obtain these cookies without storing the accountant's password, which is unacceptable.

The extension's MV3 service worker calls `chrome.cookies.getAll({ url })` to read all cookies for the portal domain, then sets a `Cookie:` header explicitly on every `fetch()` request. This is the only mechanism that works from a service worker context.

**Why not `credentials: 'include'`?** That approach was tried first. It silently fails for cross-origin requests from a service worker to `export.mpos.vn` and `portal.payoo.vn` — the cookies are not forwarded. Switched to explicit `Cookie` header in commit `c02b55a`.

## Procedures

### 1. Install and configure the extension (accountant onboarding)

1. Open Chrome → `chrome://extensions` → Enable Developer mode.
2. Load unpacked from `crm-token-extension/` in the repo.
3. Click the extension icon → enter the `GATEWAY_EXTENSION_INGEST_TOKEN` value in the popup field and save.
4. Log in to `mpos.vn` and `portal.payoo.vn` in the same Chrome profile.
5. Navigate to the GMV app. The `GatewaySyncTab` should show "Đã cài" status (detected via `localStorage["gw_ext_installed"] === "1"`).
6. Click "Đồng bộ ngay" to run a manual sync. The FE has a 180-second timeout.

### 2. Manual sync flow (trace)

```
FE (GatewaySyncTab) ──postMessage({type:"gateway-sync-now"})──► content-app-flag.js
content-app-flag.js ──chrome.runtime.sendMessage──► background.js
background.js:
  syncPayoo()   — sequential windows, JSON POSTed to /api/v1/gateway-sync/ingest-orders
  syncMpos()    — GET export.mpos.vn detail + settlement, multipart POST to /api/v1/gateway-sync/ingest
background.js ──chrome.runtime.sendMessage result──► content-app-flag.js
content-app-flag.js ──postMessage({type:"gateway-sync-now-result"})──► FE
```

The automatic background sync fires via `chrome.alarms` every 360 minutes independently of this FE flow.

### 3. Payoo crawl

The crawler iterates backwards from "now" in 3-day windows until it reaches `payoo_last_sync_at` (stored in `chrome.storage.local`) or `PAYOO_MAX_LOOKBACK_DAYS = 31` days. Windows are processed **sequentially** — one `await _fetchPayooWindow(...)` per iteration.

Each window call is protected by a **15-second `AbortController` timeout** inside `_fetchJsonCreds`. A failed window logs a warning and continues; it does not abort the entire sync.

After all windows are collected, the combined `orders` array is POSTed to `/api/v1/gateway-sync/ingest-orders`. If the ingest succeeds, `payoo_last_sync_at` is updated.

**Payoo API facts (reverse-engineered, DevTools 2026-06-16):**
- Endpoint: `https://portal.payoo.vn/api/ecom/order/`
- Query params: `PageNo`, `PageSize=100`, `From` (epoch seconds), `To` (epoch seconds), `ShopID=8971`, `Query=8971`, `isSearch=1`
- Date fields in response: strings in `DD/MM/YYYY HH:mm:ss` format (NOT epoch)
- `TotalItem` drives pagination; loop breaks on empty `OrderList`

### 4. mPOS export

mPOS exports are GET requests to a separate subdomain `https://export.mpos.vn`:

| Kind | Path | File format |
|------|------|------------|
| `detail` | `/merchant/transfer/export-withdraw-transaction` | `.xlsx` |
| `settlement` | `/merchant/transfer/transfer-list/exportCSV` | `.csv` |

Date params use `DD/MM/YYYY` strings (different from Payoo's epoch seconds). The fetched file bytes are base64-encoded and included in a multipart POST to `/api/v1/gateway-sync/ingest`.

### 5. Backend ingest

- `POST /api/v1/gateway-sync/ingest` — accepts multipart file upload, calls parsers in `mpos_import.py`, upserts to `gateway_transactions` / `gateway_settlements` with `ON CONFLICT (txn_code) DO NOTHING` / `ON CONFLICT (settlement_code) DO NOTHING`. Re-importing the same period is always safe.
- `POST /api/v1/gateway-sync/ingest-orders` — accepts `{ orders: [...] }` JSON body, calls `parse_payoo_orders`, upserts to `gateway_transactions`.
- Both endpoints authenticate via `X-GATEWAY-EXT-TOKEN` header checked against `GATEWAY_EXTENSION_INGEST_TOKEN` env var. JWT not used here.

### 6. Matching flow

1. Accountant opens `CardReconciliationTab` — lists `gateway_transactions` with `match_status != 'matched'`.
2. Clicks a transaction → FE calls `GET /api/v1/gateway-txns/{id}/match-candidates`.
3. Backend queries `payment_lines` filtered to `method IN ('card', 'installment')` and ranks by amount + date proximity.
4. Accountant selects a candidate → FE calls `PATCH /api/v1/gateway-txns/{id}/match` with `{ payment_line_id }`.
5. Backend sets `match_status = 'matched'` and records `matched_by` / `matched_at`.

Matching key: **amount + date only**. `PaymentCustomerName` from Payoo is the cardholder name and is display-only — it may be a parent, not the student, and does not reliably correspond to the app's customer field.


## Gotchas & past incidents

**`credentials: 'include'` silently dropped cookies** — Cross-origin fetches from the service worker to `export.mpos.vn` / `portal.payoo.vn` got no auth cookies with this approach. Fixed by switching to `chrome.cookies.getAll({ url })` + explicit `Cookie:` header (commit `c02b55a`).

**Parallel Payoo crawl OOM'd Render (2026-06)** — Parallelising all 3-day windows via `Promise.allSettled` caused all batches to arrive at the 512MB Render backend simultaneously, exhausting memory. Reverted to sequential in commit `5153b57`. Do NOT re-parallelize the Payoo window loop without addressing the Render memory constraint first.

**Disconnected content script caused 180s silent timeout** — After a Chrome extension reload/update, `content-app-flag.js` loses its `chrome.runtime` connection. Previously this caused the FE to silently wait 180 seconds. Fix (commit `a4fa3ba`): `content-app-flag.js` checks `chrome.runtime?.id` before `sendMessage`; if falsy, immediately posts `{ ok: false, error: "Extension đã reload — hãy refresh trang (F5) rồi thử lại." }`. Check lines 23-31 of `content-app-flag.js`.

**mPOS session expiry returns HTML** — If the mPOS session has expired, the export endpoint returns an HTML page (`<!DOCTYPE html>`) instead of xlsx/csv. The parser detects this via magic bytes and raises `ValueError: "server trả HTML (có thể chưa đăng nhập mpos.vn)"` (`mpos_import.py`, `parse_mpos_settlements`). Instruct the accountant to log in to `mpos.vn` and retry.

**mPOS "Danh sách phiếu chi" double-header** — The `.xls` settlement file has a title row at index 0 and the real header at index 1. The parser auto-detects: reads with `header=0`, checks for `created_date` column aliases; if absent, re-reads with `header=1` (`mpos_import.py` `parse_mpos_settlements`).

**Reversed mPOS transactions ("GD Đảo")** — When mPOS reports a refund, the parser creates a contra-entry row with `txn_code` suffixed `-REV`, negative amounts, and `match_status = 'ignored'`. These are never hard-deleted so the audit trail is preserved.

**Payoo order codes must be stored as text** — Order codes are 19-digit strings (e.g. `'8971260616094704777'`). If treated as `float64` by pandas, they lose precision. Always store/read as `str`.

**`needs_review` status** — Set by `_check_ambiguous_matches()` when two or more transactions share the same amount and the same minute timestamp. Surfaced to FE as `needs_review`. The public API serializes it back as `needs_review` (not collapsed to `pending`).

**Payoo installment fields unverified** — `InstallmentBankName` and `InstallmentPeriod` fields for installment transactions have not been confirmed against a real installment sample. Only online transactions were tested during reverse-engineering (2026-06-16). Treat installment Payoo field detection as unverified.

**FE still on mock data (as of 2026-07-04)** — `GatewaySyncTab.tsx` and `CardReconciliationTab.tsx` import from `card-recon/mockGatewayTxns.ts`. Real API endpoints exist in `frontend/src/lib/api.ts` (`cardRecon.*`) but the components have not been switched from mock to live. Verify this before adding FE features.

**Stale bundled zip caused 180s timeout (2026-07-06)** — the accountant installed `frontend/public/palfish-gmv-sync.zip`, which was packaged on 06-18 and missed all six 07-04 extension fixes (old `credentials:'include'` cookie path, no per-request timeouts, no disconnected-content-script guard). Symptom: "Hết thời gian — extension không phản hồi (180s)". Fix wave (commits `db0fba5` + `a07997e`, v1.3.0→1.3.1): missing-secret early error (`ok:false`, no more fake-green "0 giao dịch"), 30s timeout on mPOS file download, secret step added to the 6-step guide, `scripts/build_extension_zip.py` + `ext-version.json` version-mismatch banner. **After ANY change under `crm-token-extension/`: bump `manifest.json` version AND run `python scripts/build_extension_zip.py`** — otherwise app-downloaded installs drift from repo code again. Update procedure that preserves the saved secret: unzip OVER the same folder → chrome://extensions → Reload (⟳) — do NOT Remove + re-add (that wipes `chrome.storage.local`).

## Payoo coverage limits

Payoo's portal has at least 4 report tabs. The app pulls **only the order feed** (`/api/ecom/order/`).

| Tab | Pulled? |
|-----|---------|
| Order list (online transactions) | Yes — `syncPayoo()` |
| Card payment tab | No |
| Bank account (TKNH) tab | No |
| Installment feed | Not confirmed |

**Payoo online payment data starts T3/2026 (March 2026).** No earlier online data exists in the Payoo portal to pull.

## Validation loop

Run gates cheapest-first. Stop at the first failure — do not run higher tiers.

**Tier 1 — always (seconds):**
- If FE touched: `cd frontend && npx tsc -b` (Vercel runs `tsc -b`, not `--noEmit`).
- Check FE mock status before any API wiring change:
  ```bash
  grep -n "mockGatewayTxns" frontend/src/components/GatewaySyncTab.tsx frontend/src/components/CardReconciliationTab.tsx
  ```
- Verify volatile constants (alarm period, Payoo shop ID):
  ```bash
  grep -n "PAYOO_SHOP_ID\|periodInMinutes\|MPOS_EXPORT_BASE\|MPOS_EXPORTS" crm-token-extension/background.js
  ```

**Tier 2 — when touching extension crawl logic, parsers, or backend ingest:**
- Run backend parser tests (sandbox only):
  ```bash
  cd backend && python -m pytest tests/test_mpos_import.py tests/test_gateway_routes.py tests/test_mpos_payoo_parser_edges.py -v 2>&1 | grep -E "PASSED|FAILED|ERROR|error"
  ```
- To test the extension sync path on sandbox: load unpacked extension in Chrome Dev mode, log into mPOS/Payoo, click "Đồng bộ ngay" in the sandbox app, check the Render sandbox logs for `gateway-sync/ingest` 200 responses. Never test against prod portal sessions.

**Tier 3 — before merge/deploy only:**
- Apply any `gateway_transactions` / `gateway_settlements` schema migrations to sandbox first; confirm `ON CONFLICT DO NOTHING` upserts work by re-importing the same period and checking row counts are unchanged.
- Confirm the Payoo crawl is still sequential (grep for `Promise.allSettled` in `background.js` — must NOT appear in the window loop; parallelizing OOM'd Render in 2026-06).
- Verify `content-app-flag.js` disconnection guard (lines 23-31) still checks `chrome.runtime?.id` before `sendMessage`.

**Loop budget:** if the same gate fails twice in a row, STOP iterating. Report the failing output to the user verbatim and wait. Do not attempt a third blind fix.

**Output hygiene:** filter/grep command output for errors instead of dumping full logs into context.
