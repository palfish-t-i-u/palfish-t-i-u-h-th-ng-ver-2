## Overview

Payments flow through three layers:

1. **payment_requests** (`PR`) — top-level deal record; has target amount, received amount, state (`pending/partial/done/over/cancelled`). ID format: `PR-YYYY-NNNN`, allocated by atomic Postgres RPC.
2. **payment_lines** (lần thanh toán) — one payment attempt per PR; has `method` (`qr/cash/card/installment`), `amount`, `status` (`pending/paid/rejected`), `transfer_code`, `transfer_content`.
3. **bank_transactions** — raw bank credit rows arriving from SePay webhook or poll; linked back to a `payment_line` when reconciled.

Since Sprint 3 (decision 2026-06-19 by anh Hiếu): **PayOS is disabled** (`USE_PAYOS=false`). QR codes are self-generated by the frontend using `img.vietqr.io` against the MB Bank account. SePay webhook/poll is the sole automated reconciliation path.

**mPOS and Payoo** card transactions use a separate table (`gateway_transactions`) and are reconciled manually; their scope is đối soát only, not payment initiation.

## Jargon

- **PR (Payment Request)** — top-level deal record; ID: `PR-YYYY-NNNN`.
- **lần thanh toán (payment_line)** — one payment attempt on a PR; `method` is `qr/cash/card/installment`.
- **transfer_code** — 5-char Base36 string embedded in QR content; encodes PR year+seq+line index; used by SePay matching.
- **transfer_content** — full `addInfo` string in VietQR; max 40 chars; format: `{dial+phone} {name_truncated} {transfer_code}`.
- **is_content_stale** — computed flag: `True` when `transfer_content` on a pending QR line no longer matches current PR data (name/phone changed after QR was shown to customer).
- **name_for_transfer** — column on `payment_lines` recording which customer name (parent or child) was chosen at creation; enables stale-content detection and refresh.
- **match_status** values on `bank_transactions`:
  - `pending` — unprocessed
  - `auto_matched` — code + amount matched 100%
  - `needs_review` — code matched, amount wrong
  - `ignored` — mPOS settle noise
  - `manual_matched` — accounting matched by hand
- **discrepancy_amount** — `bank_transactions` column: received minus expected; positive = overpaid, negative = underpaid, 0 = exact.
- **VietQR** — Vietnamese QR standard built on EMV; URL template: `https://img.vietqr.io/image/{bin}-{accountNo}-compact2.png?amount=...&addInfo=...&accountName=...`

## Procedures

### 1. Webhook auth flow

The webhook at `POST /webhook/sepay` applies three security layers in order:

1. **IP whitelisting** (`_verify_ip`) — checks `X-Forwarded-For` against `SEPAY_ALLOWED_IPS`. Empty set = allow all (dev/ngrok).
2. **HMAC-SHA256** — if `X-SePay-Signature` header is present, verifies `sha256={hex}` over `{timestamp}.{raw_body}`.
3. **API Key fallback** — if no HMAC header but `Authorization: Apikey ...` is present, compares against `SEPAY_WEBHOOK_SECRET`.
4. **Production guard** — if `APP_ENV=production` and `SEPAY_WEBHOOK_SECRET` is empty, returns HTTP 503 immediately.

Anti-replay: `X-SePay-Timestamp` must be within 300 seconds of server time. Clock drift in ngrok tunnels can cause 401 rejections.

**The webhook always returns `{"success": true}` with HTTP 200**, even on processing errors — to prevent SePay from infinite retrying. Errors are logged to stdout only.

### 2. Transaction processing pipeline (`_process_sepay_transaction`)

```
1. Parse SePay timestamp → attach UTC+7 (Vietnam local, no tz info)
2. Check MPOS_SETTLE_PATTERNS → if match: match_status = "ignored"
3. _match_transfer_code_in_content → find pending QR payment_line by Base36 code
   - code match + amount match → "auto_matched", schedule mark-paid
   - code match + amount mismatch → "needs_review"
   - no match → "pending"
4. INSERT INTO bank_transactions ON CONFLICT (sepay_id) DO NOTHING  ← INSERT FIRST
5. Only after successful INSERT: mark payment_line paid + call recompute_payment_request_totals
```

Critical ordering: bank_transaction INSERT must precede marking the payment_line paid. Reversing this order creates a state where `line.status=paid` but no bank_transaction exists.

### 3. Cron fallback poll

`POST /api/v1/sepay/sync-pending` — polls `https://my.sepay.vn/userapi/transactions/list`, runs each transaction through the same processing pipeline as the webhook. Requires `reconciliation` module write permission; a `sale`-role token will 403.

### 4. VietQR generation (frontend)

`QrViewModal.tsx` builds the URL:
```
https://img.vietqr.io/image/{bin}-{accountNo}-compact2.png?amount={amount}&addInfo={transfer_content}&accountName={accountName}
```
`BANK_INFO` defaults to MB Bank BIN `970422`, overrideable via `VITE_BANK_*` env vars.

**40-char hard limit**: `img.vietqr.io` truncates `addInfo` at exactly 40 characters. The constant `_PAYOS_DESCRIPTION_MAX_LEN = 40` is defined at `payment_request_routes.py:959`. The algorithm falls back through name-shortening tiers (full name → last 2 words → last 1 word → phone+code → code only) rather than cutting the Base36 code.

**SePay VA per-order** only works with BIDV / Sacombank / VCB. MB Bank (the primary company account) does NOT support per-order VA. This is why the system matches by transfer content text rather than a virtual account number.

### 5. Stale-content detection and refresh

`_is_payment_line_content_stale` in `payment_request_routes.py` returns `True` when a pending QR line's `transfer_content` no longer matches what would be generated from current PR data.

Logic:
- Non-pending lines or non-QR lines → always `False`.
- If `name_for_transfer IS NULL` (pre-June-25 line) → compare against `child_name → name` fallback only; may produce false-positive warnings on old lines.
- If `name_for_transfer` is set → rebuild content for all current name variants (child + parent); if stored content matches any variant → not stale.

To refresh: `POST /payment-lines/{line_id}/refresh-content` (requires `paymentRequests` write permission). Only works on `pending` + `method=qr` lines.

Frontend banner: `PrStaleContentWarning` in `PaymentRequestDetailDrawer`. The `isLegacyLine` prop (`!qr.nameForTransfer`) shows different explanatory text for pre-migration lines.

### 6. Manual match (accounting)

`PATCH /api/v1/bank-transactions/{id}/match` — maps a `needs_review` bank_transaction to a payment_line. Requires `reconciliation` module write permission. Sets `match_status = 'manual_matched'` and `discrepancy_amount = actual - expected`.

### 8. Diagnose an unmatched transfer

Use this procedure when a SePay transfer did not match a PR automatically.

**Step 1 — Find the bank_transactions row**

```sql
-- In Supabase SQL Editor, replace amount and date as needed
SELECT id, sepay_id, gateway, match_status, discrepancy_amount,
       transfer_content, transaction_date, payment_line_id
FROM bank_transactions
WHERE amount = 4700000          -- replace with actual amount
  AND transaction_date::date = '2026-07-04'   -- replace with actual date
ORDER BY transaction_date DESC
LIMIT 10;
```

**Step 2 — Read match_status to determine failure mode**

| `match_status` | Meaning | Action |
|---|---|---|
| `pending` | No `transfer_code` found in content | Verify QR was shown to customer; check transfer content string |
| `needs_review` | Code matched but amount wrong | Use manual match (Procedure 6) |
| `ignored` | Matched `MPOS_SETTLE_PATTERNS` | Expected; no action needed |
| `auto_matched` | Already processed correctly | Check `payment_line_id` |
| `manual_matched` | Already matched by accounting | Check `payment_line_id` |

**Step 3 — Verify the transfer_code against payment_lines**

```sql
-- If match_status=pending, extract code from transfer_content and search
SELECT pl.id, pl.transfer_code, pl.transfer_content, pl.status, pl.amount,
       pr.id AS pr_id, pr.state
FROM payment_lines pl
JOIN payment_requests pr ON pl.pr_id = pr.id
WHERE pl.transfer_code = 'XXXXX'  -- replace with 5-char code from transfer
  AND pl.status = 'pending';
```

**Step 4 — Decide: cron poll vs manual match**

- If `bank_transactions` row is `pending` and the transfer happened recently: trigger the cron poll via `POST /api/v1/sepay/sync-pending` (requires `reconciliation` write permission). The same matching pipeline re-runs.
- If amount differs but code matches (`needs_review`): use the manual match endpoint (Procedure 6 above) or the B2 Đối soát UI.
- If no `transfer_code` in content (customer typed free text): accounting must match manually via B2 UI.

**Step 5 — Check Render logs for processing errors**

In Render Dashboard → service → Logs, filter for the transaction's `sepay_id` or timestamp. Processing errors in `_process_sepay_transaction` are logged to stdout only (the webhook always returns 200). Look for Python tracebacks or "Processing failed" entries.

### 7. Adding a new match_status value

1. Add migration to alter the CHECK constraint (see `2026-06-20-add-manual-matched-status.sql` as template).
2. Apply to sandbox first, then prod after merging to main.
3. Run `NOTIFY pgrst, 'reload schema';` in Supabase SQL Editor after applying.

## Gotchas and past incidents

**CRITICAL — cross-repo schema change risk**: `bank_transactions` is read by the separate `pf-revenue` repo (shared Supabase prod DB `jozcvbbypwvzaefteoxn`) on a 1-5 minute sliding window to push records to Lark Base "GD SePay". Schema changes here (rename columns, change types, drop columns) can silently break that sync with no error surfaced in this repo. Always coordinate with whoever maintains `pf-revenue` before migrating `bank_transactions`.

**`match_status` CHECK constraint must include `manual_matched`** (added 2026-06-20): the original migration (2026-06-13) only had 4 values. Sandbox had it fixed manually without updating the SQL file. Any sandbox reset that replays only the numbered migrations will be missing `manual_matched`, causing HTTP 500 on every manual accounting match.

**Webhook always returns 200**: do not change the return to propagate errors upward — SePay will retry indefinitely on non-200. Errors go to stdout/logs only.

**Anti-replay 300-second window**: ngrok or dev tunnels with clock drift will fail HMAC verification with HTTP 401. Either disable HMAC in dev (leave `SEPAY_WEBHOOK_SECRET` unset) or keep clocks in sync.

**`SEPAY_ALLOWED_IPS` empty = allow all**: intended for dev. In production, set to SePay's IP range to prevent spoofed webhooks. SePay may change IPs — verify at `my.sepay.vn` if webhook starts returning 403.

**mPOS SETTLE transactions**: SePay sees mPOS settlement credits as incoming bank transfers. Four regex patterns in `MPOS_SETTLE_PATTERNS` (`sepay_routes.py:43-48`) detect them and set `match_status = 'ignored'`. If a new settle pattern appears, these patterns must be updated.

**`payment_lines.amount` is `bigint`**: sending a float (e.g., `10080000.0`) via PostgREST causes error `22P02 invalid bigint syntax`. Always cast to `int` before `.eq('amount', ...)` queries.

**`payos_order_code` must be NULL (not empty string)** on SePay-only lines: Postgres UNIQUE allows multiple NULLs; an empty string would violate uniqueness across multiple lines on the same PR. See `payment_request_routes.py:2001-2005`.

**Old PayOS QR codes in the wild (since 2026-06-19)**: do not remove the `/webhook/payos` endpoint or `payos_qr.py`. If a customer pays via an old PayOS QR, SePay catches the bank transfer and accounting matches manually. The `USE_PAYOS=false` guard prevents new PayOS links from being created.

**Known FE bug — same-amount PRs (2026-06-26, "Lan Anh case")**: PR-0080 and PR-0081 had identical amounts (4.7M VND). Customer for PR-0081 paid; the UI attributed the payment to PR-0080 drawer. DB matching and `bank_transactions` were correct; the bug is in FE state/drawer management. Status: **unresolved as of 2026-07-04**. Workaround: accounting verifies by checking `bank_transactions` directly in Supabase, not relying solely on the drawer UI.

**QrViewModal race-condition guard**: `imgReadyUrl` state + `isImgFresh()` check ensure the copy/capture buttons are disabled until the new QR image finishes loading. This prevents copying the previous customer's QR when opening a new drawer in quick succession. Prod incident: 2026-06-26.

**SePay API keys rotated 2026-06-18**: update `.env.local` if the backend returns `401` from the poll endpoint.

**Customer hand-typed transfer content — ambiguous chars (2026-07-24, PR-2026-0457)**: customer typed `Fl8ZP` (lowercase L) instead of code `FI8ZP` (uppercase I) → exact match missed, txn stuck in "CK ngoài". Bank fonts render I/l identically — verify bytes with SQL `ASCII(SUBSTRING(...))`, never by eye. Fix: 2-pass matching in `_match_transfer_code_in_content` — exact first, then fold `{I,L,1}→"1"`, `{O,0}→"0"` (`_fold_ambiguous`, compare-time only, stored data untouched). Fold auto-matches ONLY with unique candidate + exact amount; ≥2 hits (exact or fold) → manual. Audit: `matched_by = system:sepay_folded` / `system:sepay_late_folded`. Do NOT "fix" the generator alphabet: `_transfer_code_hint` is deterministic base36 of `yy+pr_seq+line_seq` — switching to base31 overflows in 2028 (capacity 28.6M < 28999999) → truncation collisions. See `docs/learnings/fold-ambiguous-chars-transfer-code-match.md`; tests: `tests/test_sepay_fold_matching.py`.

## Validation loop

Run gates cheapest-first. Stop at the first failure — do not run higher tiers.

**Tier 1 — always (seconds):**
- If FE touched: `cd frontend && npx tsc -b` (must pass — Vercel runs `tsc -b`).
- Spot-check volatile constants still match documented values:
  ```bash
  grep -n "_PAYOS_DESCRIPTION_MAX_LEN" backend/payment_request_routes.py
  grep -n "bin\|accountNo" frontend/src/constants/bank.ts
  ```

**Tier 2 — when touching webhook, matching logic, or `bank_transactions` schema:**
- Trigger the sandbox cron poll (never prod); verify no 4xx/5xx in Render sandbox logs:
  `POST /api/v1/sepay/sync-pending` with a `reconciliation`-write token (sale tokens will 403).
- Confirm `match_status` CHECK constraint is intact in sandbox Supabase SQL Editor:
  ```sql
  SELECT pg_get_constraintdef(oid) FROM pg_constraint WHERE conname = 'bank_txn_match_status_check';
  ```
- Run Diagnose procedure (Procedure 8) on a known sandbox transaction — filter Render logs
  for `sepay_id` or timestamp; look for tracebacks, not full log dumps.

**Tier 3 — before merge/deploy only:**
- Apply migration to sandbox first; run `NOTIFY pgrst, 'reload schema';` in sandbox SQL Editor; confirm ingest endpoints return 200.
- Verify `pf-revenue` Render service is unsuspended and Lark sync is unbroken by any `bank_transactions` column change (cross-repo risk — coordinate before merging to main).
- Confirm `match_status` CHECK includes `manual_matched`; a sandbox reset replaying only migrations pre-2026-06-20 will lose it.

**Loop budget:** if the same gate fails twice in a row, STOP iterating. Report the failing output to the user verbatim and wait. Do not attempt a third blind fix.

**Output hygiene:** filter/grep command output for errors instead of dumping full logs into context.
